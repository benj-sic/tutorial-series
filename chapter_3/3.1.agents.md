# 3.1 How AI Agents Work

## 3.1.1 From Workflows to Agents
In the previous chapters, we saw that LLMs can help automate many research workflows. At first glance this is pretty amazing, mindblowing in fact. But is this enough? 

For example you can ask an LLM "What are common tumor suppressing proteins in humans?". The LLM will use information learned during training to provide an answer. In Chapter 2, we use Python to retrieve scientitic publications and database entries for the model. But it was our code that determined whcih steps to take and when, not the model. The limitation with LLM workflows is that while the language models can provide responses (i.e., "think") they cannot "act". 

An **agent** gives the LLM a more active role in that process. If you ask for publications supporting an answer, an agent with a literature-search tool could decide to search, inspect the results, and search again if needed. The model chooses among the tools available to it, while the surrounding code executes those calls and sets limits on what it can do. This repeated cycle of choosing an action, observing its result, and deciding what to do next is called an **agent loop**.

**Here are some example use cases of AI agents in science**
- Searching the literature
- Automating data analysis
- Generating hypotheses
- Evaluating models/agents
- Writing technical reports

The examples that follow show how to give an LLM tools, run the agent loop, and use the results to answer a scientific question. First, we'll define the parts of that loop and how they fit together.

## 3.1.2 Components of an AI Agent

### Agents

In the simplest terms, an AI agent uses an LLM to choose actions, observe their results, and decide what to do next. In the examples in this chapter, those actions are calls to tools. The agent continues until it can answer the question or reaches a stopping condition.

Like a cell sensing signals in its environment and responding to them with movement or cell signaling, an AI agent similarly receives information and takes actions defined by the software environment around it.

One approach to building language-model agents is **ReAct** (Reasoning and Acting). In ReAct, the model interleaves reasoning steps with actions, then uses the resulting observations to guide its next step. Read more here: [Yao et al., *ReAct: Synergizing Reasoning and Acting in Language Models*](https://arxiv.org/abs/2210.03629).

### Environments

The **environment** is is everything outside the agent that the agent can interact with. This could could be a virtual environment (like a game word or a simulation), a physical system such as a robot in a lab, or a codebase that provides access to datasets and web APIs.

### States and Observations

A **state** is a snapshot of the agent’s current situation (i.e., what the agent knows at a particular point in a task). The agent may see only part of the state through an **observation**, such as the result of a tool call. The agent can use that result, along with the context from earlier steps, to decide what to do next.

For a cellular agent, this might be the concentration of nutrients nearby. For a software agent, it might be data it has gathered. You can think of the state as the agent’s current understanding of the environment.

### Tools

**Tools** let an agent retrieve information or take actions. An agent answering a biology question might have tools for searching papers, retrieving protein records, or analyzing a sequence. In software, a tool may be a Python function, a web API, or a data-analysis module. Its name, description, and expected inputs help the model decide when and how to call it, this is called the **tool schema**.

### Harnesses

The **harness** is the software that runs the interaction between the agent and its tools. It sends the taks and available tool definitions to the model, executes requested tool calls, returns their results, and checks whether to continue or stop. We will build this loop in the following sections.

### Key Concepts to Remember

| Concept | Plain English |
|---------|--------------|
| **Agent** | Uses an LLM to choosewhat to do next based on the task and information received |
| **Tool** | A function or API the AI can choose to call |
| **Tool schema** | The tool's name, description, and expected inputs |
| **Observation** | Information returned after an action, such as a tool result |
| **Harness** | Software that runs the model-tool interaction and manages when it stops |
| **Agent loop** | Choose an action &rarr; run the tool &rarr; observe the result &rarr; choose the next step or answer |

## 3.1.3 FutureHouse Agents for Scientific Discovery

At FutureHouse, we seek to accelerate scientific research with an AI agents designed to automate many of the critical steps on the path toward scientific progress. We have built a series of AI agents specialized for tasks including information retrieval, information synthesis, chemical synthesis design, and data analysis. 

As introduced in Chapter 2, [PaperQA2](https://github.com/Future-House/paper-qa) is a system for retrieving and answering questions about scientific literature. [Finch](https://github.com/Future-House/finch) is a data-analysis agent that takes a dataset and a research question, then iteratively works through a Jupyter notebook to produce an analysis and answer.

[Robin](https://www.futurehouse.org/research-announcements/demonstrating-end-to-end-scientific-discovery-with-robin-a-multi-agent-system) combines specialized agents in a workflow for scientific discovery. In a study of dry age-related macular degeneration (dAMD), Robin helped idenify ripasudil, a Rho-kinase (ROCK) inhibitor clinically used to treat glaucoma, as a novel therapeutic candidate for further investigation. 

Building on this work, [Kosmos](https://edisonscientific.com/articles/announcing-kosmos) is an AI scientist developed by Edison Scientific, a spinout of FutureHouse. Kosmos uses structured world models to incorporate information from hundreds of agent trajectories and maintain a research objective across a much longer investigation.This allows Kosmos to maintain coherence towards a specific research objective over tens of millions of tokens.

## 3.1.4 Limitations of AI Agents

Tools can help an agent complete tasks that an LLM could not complete from its training alone, but they do **not** guarantee a correct result. Mistakes can arise from the model's decisions, the information returned by a tool, or the way the harness handles each step. Let's take a look some limitations faced by AI agents:

* **Context window constraints** LLMs have a finite context window. In multi-step agentic workflows, the accumulation of messages and tool calls can quickly cause the model to approach or exceed this limit. At this point, earlier information must be removed or summarized. When this compaction occurs, the agent may lose access to details it needs, repeat steps, or contradict earlier findings.

* **No persisent memory by default**  Whether information survives between runs depends on how the agent is built. Without a way to save and retrieve previous context, a new run will not have access to results from a earlier one. Persistent records can help the agent reuse prior work, but they do not mean that the model has learned.

*  **Hallucinations and unreliable tool outputs** An LLM can generate plausible but incorrect response. Tool calls may also be incomplete, outdated, or misinterpreted. Access to a source does not ensure that the agent uses it correctly.

* **Error propagation across steps** A wrong tool choice, a misinterpreted observation, or a malformed argument can cascade through subsequent steps and compound into a larger failure. Errors are not always recoverable, especially if the agent lacks explicit error-handling logic.

* **Incomplete or premature termination** Agents driven by a fixed step budget may terminate before completing a task, may call a termination tool too early because the LLM misjudges task completion, or continue calling tools when it should stop. A final answer is not necessarily evidence that the taks was completed successfully.

*  **Limited generalization across tasks** Agents are sensitive to how tools are described and how prompts are framed. A system prompt or tool description that works well for one task may perform poorly on a different one. Agents often lack the robustness to handle out-of-distribution inputs gracefully.

### Mitigations & Performance Improvements

| Limitation | Mitigation|
| --- | --- |
| Context overflow | Summarize or compress old messages; use sliding window memory; set output length limits on tool responses |
| No persistent memory | Add a vector store or structured cache to persist and retrieve results across runs |
| Hallucinations or unreliable results | Check claims against retrieved sources and validate important tool outputs |
| Error propagation | Add explicit error handling and retry logic; validate tool inputs/outputs before passing them downstream |
| Premature or missing termination | Define completion criteria and set step limits and stopping conditions |
| Poor generalization | Test with varied questions, datasets, and tool responses |

## 3.1.5 Evaluating AI Agents

Evaluating an agents is as important as building it. An **evaluation** (or **eval**) gives an agent a task and checkts its performance against defined criteria. A **benchmark** is a collection of tasks and scoring methods that can be used to compare systems. When evaluating an agent, the system being tested includes its model, tools, and harness, not just the underlying LLM ([Anthropic, *Demystifying Evals for AI Agents*](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

A final answer alone may not show how the agent reached it. We can also examine its **trajectory**, the record of its actions and observations:

- **Answer quality:** Did it address the question accurately and support its claims?
- **Tool use:** Did it call the right tools with valid arguments?
- **Trajectory:** Did it use the information it retrieved, or did it waste steps?
- **Failure modes:** Did it recover from errors, stop too early, or claim to have completed work it did not do?

FutureHouse and Edison Scientific have developed benchmarks for different parts of scientific research. [LAB-Bench](https://www.futurehouse.org/research/lab-bench-measuring-capabilities-of-language-models-for-biology-research) and its successor, [LABBench2](https://advances.edisonscientific.com/research/labbench2-an-improved-benchmark/), test tasks such as retrieving scientific information and working with biological sequences. [BixBench](https://www.futurehouse.org/research/bixbench) tests agents on multi-step bioinformatics analyses using research questions and datasets; [BixBench3](https://advances.edisonscientific.com/research/bixbench3-benchmarking-study-scale-computational-biology/) extends this work to longer, research-study-scale tasks.

These benchmarks help reveal strengths and failure modes, but a score applies to the tasks and testing conditions used. It does not establish that an agent can perform every lind of scientific research.
